# Project documentation — yurosenagar.com

The four documents that define this project: what it is for, how it looks, how it is built, and what happens next.

| # | Document | Answers |
|---|---|---|
| 01 | [Product Requirements](01-product-requirements.md) | **Why** does this exist? Who is it for, what must it do, how is success measured? |
| 02 | [Design](02-design.md) | **How does it look and feel?** Principles, tokens, typography, components, theming, responsive behaviour. |
| 03 | [Technical Requirements](03-technical-requirements.md) | **How is it built?** Stack, architecture, data model, standards, security, performance, deployment. |
| 04 | [Implementation Plan](04-implementation-plan.md) | **What happens next?** Phases, tasks, acceptance criteria, working method, risks. |

## Reading order

- **New to the project?** 01 → 03 → 02 → 04.
- **Making a visual change?** 02, then the definition of done in 04.
- **Adding a feature?** 03 for architecture, 04 for the workflow.
- **Planning the next session?** 04, section 10.

## Keeping these honest

These are living documents. When the code and a document disagree, fix the document — an out-of-date spec is worse than none. Review at the end of each phase (task 4.6).
